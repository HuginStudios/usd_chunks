    Writing a chunk module⚓︎

    In short: a chunk is a Python module. main() sets up its params, execute(node) does the work, and config() holds details like its description and category.

    This page is about writing a new chunk. To make and wire chunks you already have from Python, see Scripting.

    A chunk module is a plain .py file. Put it anywhere in a USD_CHUNK_DIRS folder and it's found automatically. You don't need to register it, write a plugInfo.json, or import it anywhere.

    A module can define up to four top-level functions. Only main() is required.

    Function Required Called
    main() yes Once per instance, to build a Chunk object. Each node you add to the graph, and each chunk prim loaded from a file, is a separate main() call.
    config() no Once, when the module is found, for its settings (ChunkConfig).
    execute(node) no Every time the chunk cooks. See execute().
    commit(node) no Once per chunk, after everything has finished cooking. See commit().

    main()⚓︎

    from usd_chunks import chunk


def main():
    button = chunk.Button("add_cube", "Add Cube")
    button.add_callback(add_cube)

    chunk_api = chunk.Chunk("Add Cubes")
    chunk_api.add_param(button)
    return chunk_api

    main() takes no arguments and must return a chunk.Chunk. A Chunk is a Group that also keeps track of its layer, its DAG node and its exec ports. Create its params and groups here, and add their callbacks with add_param and add_callback.

    main() runs once per instance, not once when the module is found. Finding the module only imports it and checks that main() exists. After that, main() is called every time a chunk is created: once for each node you add, and once for each saved chunk prim when a file is opened. So anything slow in main(), like building a lookup table, runs again for every node. If that matters, cache it at module level.

    Don't change the stage in main(). It runs before the chunk has its prim and its own layer, so anything it writes lands in the wrong place. Anything that changes the stage goes in a callback, in execute(), or in commit().

    Callbacks hear their own chunk, never another one. Chunks talk to each other only through wires: an exec input, or an @Node.param@ expression. Both are drawn in the graph and saved in the file. A change in a chunk above yours reaches your chunk as a cook of your execute(), not as a notice. So:

    • add_callback(..., sender=...) takes your own chunk or one of its params. Another chunk's param raises a ValueError.
    • listen_globally=True is for the stage and the host only: stage edits, prim selection, the viewport camera. Listening globally to another chunk's notices (CHUNK_CHANGED, PARAM_CHANGED, ...) raises a ValueError.
    • A param can't depend on another chunk's param through add_dependency. Use connect_value, which writes the expression for you.

    A stage listener stays small. When you do listen to the stage or the host:

    • Read the stage and set only your own chunk's params. Never author USD in the callback. execute() authors from the params, so the change reaches the chunks wired below. Camera's Lock to Free Camera works this way: the freecam sets translate and rotate.
    • Write only when the value actually changed. Every write can cook your chunk.
    • Wait for CHUNK_LOADED before writing. Saved values are restored after main(), and a write before then can overwrite them.
    • Return early on rounds that can't matter to you. A stage listener runs on every stage change, for every instance of your chunk.

    Most of the time you don't need a listener at all. A menu of what's on the stage (the cameras, a prim's variant sets, the SkelRoots) is only needed when someone opens it. Give your module a menu_items hook instead, and every frontend asks it as the menu opens:

    def menu_items(node, param_name):
    if param_name == "camera":
        return [str(p.GetPath()) for p in node.get_stage().Traverse() if p.IsA(UsdGeom.Camera)]
    return None   # this menu keeps its items

    The current value always stays listed, so a saved pick survives until the stage offers it.

    A chunk that follows the host application's own scene (Blender's objects, say) defines host_changed(node). The host calls it, debounced, after the user edits the scene; the module decides whether what it reads moved and calls node.execute() if so. Blender's add-on calls it today; see chunks/modelling/blender_import.py.

    docs/example.md has a longer example with notes on the param types, groups, flags and callback signatures you can use in main().

    Icons in the node graph⚓︎

    A node shows an icon in its header, and a group can show one beside its name. Only the chunk decides them; nothing else picks one, so a chunk or group that sets no icon shows none.

    The node's icon goes in config(), so every node of the chunk gets it:

    def config():
    return chunk.DefaultConfig(
        category=chunk.StandardCategory.MODELLING,
        icon="posts",
    )

    A group's icon goes on the group, in main():

    run_grp = chunk.Group("Run", icon="ruler", flags=_GF)

    icon takes either:

    • the name of a built-in icon: a file name, without .svg, from usd_chunks/resources/icons/node/ (sun, move, rotate, cube, camera, eye, ...). Built-in icons are drawn in one colour, and each has a default colour.
    • a path to your own image file (.svg or .png), drawn as it is.

    On a group or a param, anything else raises a ValueError.

    Which icon a node shows, first match wins:

    1. The icon on the chunk's prim in USD (see below), for that one node.
    2. icon set on the chunk in main() (chunk_api.icon = "sun"), for every node of it.
    3. icon in config().

    Per node, in USD. A node's icon and colour can also be set on its chunk prim, through USD's own UsdUINodeGraphNodeAPI. These are saved in the file, and the node updates as soon as they change:

    from pxr import Gf, Sdf, UsdUI

api = UsdUI.NodeGraphNodeAPI.Apply(chunk_prim)
api.CreateIconAttr().Set(Sdf.AssetPath("camera"))          # a built-in name or an image path
api.CreateDisplayColorAttr().Set(Gf.Vec3f(1.0, 0.4, 0.3))  # the icon's colour

    The lookup is usd_chunks/chunk_icons.py, so any graph frontend can show the same icons.

    config()⚓︎

    from usd_chunks import chunk


def config():
    return chunk.DefaultConfig(
        category=chunk.StandardCategory.MODELLING,
        description="""
        Resets a prim's transform: clears every authored transform op.

        Writes an empty xformOpOrder on the prim, so none of its transform ops apply.
        """,
    )

    The description opens with one summary line, then a blank line, then the details. The summary line says what jobs the chunk does, in the words someone asking for them would use, in at most 90 characters, without repeating the chunk's name. It sums up the text below it, so it claims nothing that text doesn't say. usdchunks list and the create menu's search show only that line, so it decides whether a person or an agent finds the chunk at all.

    config() returns a chunk.DefaultConfig, a small subclass of chunk_core.ChunkConfig. It describes how the chunk is loaded and how it shows up in menus. A module without config() gets the defaults below.

    Field Default Meaning
    category "Chunks" Where the chunk appears in the create menu. Use a StandardCategory member (MODELLING, DYNAMICS, TRANSFORM, UTILS, RIGS, USER, EXAMPLES, USD, PROPERTIES, USD_RENDER, USD_LAYER, CORE, MATERIALS, MTLX) or a plain string for your own.
    description "Chunk description..." Shown in tooltips and the create menu. ChunkGroup's doc param uses the same text to describe what a saved network does, for a person or an AI reading the file.
    load_for_plugin None Only load the chunk in one host plugin (e.g. "chunk_usdview"), if it only works there.
    hosts [] The applications the chunk runs in, each a name with an optional minimum version: ["houdini>=21.5", "blender>=5.1"]. Empty or not set: every host. Elsewhere the chunk is skipped. Import a host-only module (bpy, hou) under try/except ImportError, so other hosts can still read config().
    requirements [] pip packages the module needs, e.g. ["numpy>=2,<3"]. If one is missing and the module fails to import, it's skipped instead of crashing. usdview and usdchunks run ask whether to install the missing ones into USD_CHUNK_DEPENDENCY_DIR (see USD_CHUNK_AUTO_INSTALL).
    required_modules [] Other chunk modules that must be loaded for this one to work.
    interactive False The chunk writes to a file layer that is kept, instead of its own layer being rebuilt on every cook. Use it for a chunk that makes a one-off edit rather than something that is re-cooked.
    cache_cook False Keep this chunk's cooked result on disk and read it back instead of cooking again, when nothing it depends on has changed. For a slow cook whose result depends only on its params, the files they name and the stage's units. See Caching a slow cook.
    cache_always False cache_cook that can't be turned off: no Cache Result checkbox, USD_CHUNKS_COOK_CACHE=0 doesn't apply, and quick cooks are stored too. For a result that is expensive or impossible to remake anywhere else, such as Blender Import's.
    cook_on_open False Cook this chunk every time a network opens, instead of reading back the result kept when it was saved. For a result that depends on something no key can see: the clock, an unseeded random, a web request. See Opening without cooking.
    hidden False Left out of the create menu. For a type that is only saved and loaded, never created by hand, like runtime, the type a chunk built in Python is saved as (see Building a chunk at runtime). It still has to be a registered module, because that's how loading a file knows what to rebuild.
    terminal False The chunk has no outputs:chunk, so it ends an exec chain. The View and Output chunks use this.
    exec_inputs 1 How many numbered exec input ports the chunk has. 1 is the normal case: one inputs:chunk port, which can still take several wires. With more than 1, each slot gets its own port and it matters which wire goes where. For example, Stage Expression Switch has a normal path on slot 0 and a matched path on slot 1, and only one of them runs.
    dynamic_exec_inputs False The chunk adds a new numbered exec input port for each wire connected to it, plus one empty port for the next one. For chunks like Merge or Switch, where each incoming branch needs its own port. Unlike exec_inputs, the number of ports isn't fixed.
    outputs [] Extra typed output ports beyond outputs:chunk, as [(name, SdfTypeName), ...].
    variants [] Extra entries in the chunk's submenu in the create menu, as [(label, {param: value}), ...], or a function that returns that list. Use a function when the list is slow to build (for example, listing a shader registry). It then only runs the first time the menu is shown, not every time chunks are loaded.
    gizmos [] Viewport handles that control this chunk's params. See Chunk gizmos: the host contract.

    Keep config() self-contained. When the module is found, config() is run on its own, with only the module's usd_chunks imports done. This way, reading a module's config never runs the rest of its code. If config() uses a constant or helper from the module, the first try fails with NameError. The registry then tries once more after running the module's top-level assignments and defs. If any of those need a non-usd_chunks import, that fails too, and the module falls back to the DefaultConfig() defaults: wrong category, generic description, and only a warning in the log. If config() needs something slow to build, pass a function to variants (see the table above) instead of a constant built in the module.

    execute()⚓︎

    def execute(node: chunk.Chunk) -> None:
    ...

    execute is a reserved name at module level. Don't use it for a normal callback, or it will be called every time the chunk cooks.

    If a module has execute(node), it runs every time the chunk cooks: when something it depends on changes (add_dependency), when the chunk is loaded from a file, or when the exec chain is run again. On load, param values are restored, but callbacks don't run again (see below). node is the chunk itself, the same object main() returned. So execute usually calls node.get_stage() or node.get_edit_context() and then changes the stage.

    It runs with a Usd.EditContext already set to the chunk's own layer (unless the chunk is interactive, which writes somewhere else). Every execute() starts from an empty layer, so write the whole result every time. It must give the same result every time it runs with the same inputs, in the same order: a prim written in dict or set order moves about. It can run many times while the graph cooks, so keep it fast.

    The framework then changes the chunk's layer only where the result differs (a diff cook): a prim that comes out the same sends no change, and a changed value is set in place, so the viewport updates it rather than building it again. For that, the cook runs on a stage of the layers upstream of the chunk, writing into a scratch layer. Read and write through node.get_stage() and node.get_edit_context(), never the scene's stage (node.get_scene_stage()), which doesn't hold that layer; keep the scene's stage for the scene's own bookkeeping, such as wiring chunk prims. Key anything kept between cooks on node.get_layer_identifier(), not the edit layer's identifier. A chunk that changes the layer stack or what is muted, or sublayers its own layer, is cleared and rewritten instead. USD_CHUNKS_DIFF_COOK=0 turns diff cooks off.

    You write execute(node); you don't call it directly. To run a chunk again, call chunk.execute(): it re-executes the chunk and everything that depends on it, the same as when a param changes. Changing a param or a wire already does this, so a module only needs it when its result is out of date in a way no param change says -- say, it restored params its first cook could not see.

    An execute that sets many params -- a Wedge writing a variant's ranges -- sets them inside with chunk.change_block():. Then what they drive cooks once, after the last one, rather than once per value.

    A common pattern is a chunk that does its real work in a param callback, with execute only there to redo that work after the file is opened. This is why execute exists, instead of doing everything in callbacks:

    def _run(owner, notice, sender):
    ...
    UsdGeom.Xformable(prim).ClearXformOpOrder()


def execute(node: chunk.Chunk) -> None:
    """load_chunks calls this once per chunk after bulk-restoring its param values, so a
    reloaded chunk actually redoes its work — the real logic lives in _run, a Button
    callback, which load's value-restore deliberately does not trigger."""
    _run(node, None, None)


def main():
    chunk_api = chunk.Chunk("Reset Transform")
    ...
    run_btn.add_callback(_run)
    return chunk_api

    (the full version is chunks/transforms/reset_transform.py). A save only stores a chunk's data (params, values and wiring), never the code that ran (see What a save keeps). execute is what makes a chunk do its work again after the file is opened.

    Caching a slow cook⚓︎

    Before caching a slow cook, check whether it needs to be slow. Authoring thousands of prims through the Usd API, or looping over points in Python, is usually 10× or more slower than it has to be. See Making a chunk fast.

    Because a cook with the same inputs always gives the same layer, a slow one doesn't have to run again. Set cache_cook=True in config() and the result is kept on disk and read back the next time the inputs match, including after the file is closed and opened again:

    def config():
    return chunk.DefaultConfig(cache_cook=True)

    The cache compares everything it can see:

    • every param's value (an expression counts as the value it resolves to), except labels and OUTPUT params, which the cook writes;
    • the size and modification time of any file a param names;
    • the module's own code and the files next to it;
    • the stage's up axis and metersPerUnit.

    If the result also depends on something that is not a param, for example geometry read from an upstream chunk or files named inside another file, add a cache_key(node) function that returns it. Anything that can be repr()ed works. Return None when it can't be worked out, and the chunk cooks as usual:

    def cache_key(node):
    return [mesh_checksum(prim) for prim in input_meshes(node)]

    Poly Reduce returns a checksum of the meshes it reads, and URDF Import returns the size and date of each mesh file the .urdf names.

    Some results are not made in a cook: a simulation bakes when you press Run, on a worker thread. To cache one, take the entry when the work starts and store the layer when it is done. The next cook with the same inputs reads it back, also after the file is opened again. Taking the entry first means a param changed during the bake does not relabel it:

    def cache_key(node):
    return sim_bake.input_key(node)  # None in ordinary cooks: no automatic caching

entry = sim_bake.cache_entry(node, sim_bake.digest(job))  # None when caching is off
if entry is not None and entry.restore(node, layer):
    ...                               # read back: no bake
...                                   # else bake into the chunk's layer, then
if entry is not None:
    entry.store(node, layer)

    cache_key answers only while cache_entry asks, because working out a bake's inputs can take seconds, too slow for every cook. The RBD Solver and the Particle Solver do this.

    Each chunk of such a module gets a Cache Result checkbox, on by default, to switch caching off for that one node. Only cooks that take longer than about 50 ms are stored, since reading a result back takes time too. A cook that changes its own input params, or adds params, is never stored. For where the cache lives and how to switch it off, see USD_CHUNKS_COOK_CACHE.

    Opening without cooking⚓︎

    A saved network holds the chunks and their wires, not their results. So when you save, each chunk's layer is also kept in the cook cache, and when the network is opened again, each chunk reads its layer back instead of cooking, as long as nothing it depends on has changed. This is for every chunk; cache_cook is not needed.

    A chunk's result is read back only if all of these are the same as when it was saved:

    • everything cache_cook compares (its params, the files they name, its module's code, the stage's units);
    • its exec wires and what the framework keeps on its chunk prim;
    • the same for every chunk upstream of it;
    • the network file's own prims and time range, and the size and date of the files it sublayers or references.

    Otherwise it cooks, as it always did. A chunk whose last cook also wrote outside its own layer (into the session layer, like a MaterialX Shader's input wires) or changed the layer stack always cooks. So does a module that sets cook_on_open=True.

    To switch it off, set USD_CHUNKS_OPEN_CACHE=0.

    Long bakes: sim_bake⚓︎

    A simulation that takes seconds or minutes must not stop the host. Write the bake as a generator and hand it to sim_bake.run. Read the scene first, then yield sim_bake.WORKER: what follows runs on a worker thread, so it must not touch USD. yield sim_bake.MAIN comes back to the main thread to write the result:

    from usd_chunks import sim_bake

def bake(ctx):
    job = read_inputs(stage)          # main thread
    yield sim_bake.WORKER
    result = solve(job, progress=ctx.progress, cancelled=ctx.cancelled)
    yield sim_bake.MAIN
    write_result(stage, result)       # main thread
    return result

sim_bake.run(node, bake, report=show_in_readout, finish=when_done)

    Headless and under test there is no event loop to come back to, so the bake runs straight through. sim_bake.cancel(node) stops it.

    Some engines hold Python's GIL while they compute (Taichi does), which stops the UI even from a thread. Call the solve through sim_bake.in_subprocess(ctx, solve, **job) to run it in a separate Python process. promote, keep and restore handle the bake's layer: put it in front of the layers it animates, and put it back after the next cook rewrites it.

    For smaller work of your own -- a download, a wait before re-running -- get back to the main thread with node.get_scene().call_later(fn, delay=0.0). It works in every host (usdview, Blender) and from any thread, and returns a function that cancels the call, which is all a debounce needs:

    def _schedule(node):
    cancel = getattr(node, "_pending", None)
    if cancel:
        cancel()                      # a newer change: the last wait no longer counts
    node._pending = node.get_scene().call_later(lambda: rerun(node), delay=0.6)

    Don't import Qt for this. A chunk that imports PySide6 doesn't load in a host without it.

    Skipping cooks nothing reached⚓︎

    A change to a chunk dirties everything below it, but most of those chunks read nothing that changed: a Scatter below a Light doesn't care that the Light turned. So a chunk that only the chunks above it changed doesn't cook unless one of them changed a prim it reads.

    What a chunk reads is not declared anywhere. During a cook, node.get_stage() returns a stage that only holds the chunk's inputs (the prims its prim path params name, such as PRIM_SELECTION params and primpath_location) and the prims its last cook wrote. So:

    • Read the prims you need through a prim path param, not a path written into the code. A chunk that looks up anything else, or walks the whole stage (Traverse()), is noticed, cooked again on the whole stage, and never skipped from then on. It still works; it just always cooks.
    • Framework work on the scene, like muting a gate's branches, goes through node.get_scene_stage(), which is always the whole scene. Module code shouldn't need it.

    Anything the framework can't account for makes the chunks below cook, as they always have: a rewire, a chunk disabled above, a change to which layers are muted or to the stage's expression variables, an Edit Target repointed.

    commit()⚓︎

    def commit(node: chunk.Chunk) -> None:
    ...

    commit is for a chunk whose job is writing a file, not writing to its own USD layer, for example Export USD or a render product chunk. It's separate from execute because they run at different times:

    • execute runs many times while the graph cooks and params change. It's the right place for fast USD edits, and the wrong place for writing to disk.
    • commit runs once, after everything has finished cooking. usdchunks run calls it, and so does Scene.commit() from Python. usdview doesn't call it on its own; a chunk like Export USD has a button for that. Chunks commit in graph order, so a chunk that reads another chunk's output sees the finished result.

    No edit context is set up for commit. It reads the final composed stage and writes to disk. Modules without commit are skipped, since most chunks have nothing to write. A disabled chunk, or one that isn't connected to the active view, never commits.

    Lofting params a module builds at runtime⚓︎

    Lofting publishes a param's saved attribute on its group. A param flagged TRANSIENT has none: it's session state, rebuilt rather than saved. A module whose transient params should still be loftable (Property Editor's fields are) defines these:

    def promote_param(node, param):
    """Return a saved param to loft in place of the transient `param`, or None."""

def restore_params(node, prim):
    """On load, before saved values are read back: build the promoted params again."""

def param_unlofted(node, param):
    """`param` was just unlofted from its group."""

    promote_param runs when a transient param is lofted, and the group publishes the param it returns. That param isn't in what main() builds, so on load restore_params builds it again from the chunk's prim, before its value and its link to the group are restored. Property Editor keeps the list of promoted attributes in a hidden saved param for this.

    Discovery, recap⚓︎

    Every folder in USD_CHUNK_DIRS, including subfolders, is searched for .py files. Any file with a top-level main() is registered under its file name. There are no other rules for folder layout or file names. Environment variables explains which one wins when two folders have a chunk with the same name.

    To check what was found, run usdchunks list (or usdchunks list <word>). usdchunks show <name> prints a chunk as someone looking for one sees it: its description, its menu entries and every param, with its type, default and range.
